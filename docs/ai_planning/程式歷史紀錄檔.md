## 📌 版本演進與修改歷史紀錄

### [2026-08-30] 修訂 1：定位 Turnstile 驗證機制與 Token 生命週期
* **問題現象**：
  雲端排程在執行到第 40~50 檔時頻繁出現連續採集失敗，重試後依然無法取得資料。
* **根因分析**：
  TPEX `brokerBS.html` 前端所使用的 Cloudflare Turnstile 驗證 Token 是**單次消耗品 (Single-Use Token)**。表單一旦提交，該 Token 即被 TPEX 後端驗證並作廢。若未主動調用 `window.turnstile.reset()` 並等待新 Token 生成，後續查詢會被 TPEX 拒絕。
* **修改思維與對策**：
  1. 在每次點擊查詢後，立刻執行 `window.turnstile.reset()` 觸發背景重簽。
  2. 在發起下一檔查詢前，輪詢等待取得全新且長度大於 50 字元的有效 Token。

### [2026-08-30] 修訂 2：TPEX 雲端分散式分片架構 (Matrix Sharding)
* **問題現象**：
  單一 GitHub Actions Runner 採集全市場 1,002 檔標的耗時長達 35~45 分鐘，長時間運行易遭遇 GitHub 虛擬機連線中斷或 Cloudflare 對單一 IP 的高頻限流。
* **根因分析**：
  單一 IP 在短時間內連續發起數百次帶有 Turnstile 的 POST/GET 請求，會觸發 Cloudflare 頻率限制 (Rate Limiting)，返回 `操作逾時`。
* **修改思維與對策**：
  1. **20-Shard 分散式矩陣**：將全市場 1,002 檔標的均分給 20 個獨立 Runner（每台僅需處理 ~50 檔，耗時縮短至 2~3 分鐘）。
  2. **錯峰啟動 (Staggered Startup)**：每台 Runner 錯開 6 秒啟動，避免 20 台同時撞擊 TPEX 首頁。
  3. **二次自動聚合 (`merge-tpex`)**：20 個分片產出 Parquet 碎片後，由獨立 Job 自動下載合併、產生彙整日誌並同步至 Google Drive。

### [2026-08-30] 修訂 3：TPEX 首次載入 Session 預熱與 WARP 網絡切換延遲修復
* **問題現象**：
  部分分片第 1 檔（如 `1259`）出現 `非預期回應: 操作逾時，請重新整理頁面後再試`；且當連續失敗觸發 WARP 換 IP 後，後續標的連鎖失敗。
* **根因分析**：
  1. **首頁 Session 握手時間**：TPEX `brokerBS.html` 在載入後，PHP Session 與前端 JS 上下文建立需要 4.0 秒。若頁面載入後 2.5 秒內即點擊查詢，TPEX 伺服器判定 Session 尚未建立，返回 `操作逾時`。
  2. **WARP WireGuard 握手延遲**：執行 `warp-cli connect` 後，Linux 虛擬機的 DNS 與路由表需要 5~8 秒完成握手。原先僅等待 2.5 秒，導致重啟後的 Chrome 在無網絡連線狀態下載入頁面，造成後續標的連鎖崩潰。
* **修改思維與對策**：
  1. 首頁首次載入等待時間調整為 **4.0 秒**，確保 Session 完備。
### [2026-08-30] 修訂 9：頻率調控與 8-Shard 錯峰降載架構（消除 TPEX 後端保護性逾時）
* **問題現象**：
  在 20-Shard 併發下，雖然單一節點標的數少 (~50 檔)，但多節點高頻查詢與重啟導致 TPEX 後端資料庫負載過高，頻繁觸發「操作逾時」，且重啟 Chrome 的開銷最終導致 Runner 超時 (25 分鐘)。
* **根因分析**：
  TPEX `brokerBS.php` 是傳統關聯式資料庫查詢，需彙整全市場單一股票之數千筆買賣分點。若發送間隔過密 (<1.5s) 或 20 節點同網段併發，TPEX 伺服器會啟動後端過載保護（Backoff Throttling）。
* **修改思維與對策**：
  1. **單檔查詢間隔拉寬 (3.5 秒)**：成功獲取後溫和等待 3.5 秒（無交易標的等 2.0 秒），給予 TPEX 資料庫足夠釋放時間。
  2. **收斂至 8-Shard 矩陣 (每台 ~125 檔)**：降低雲端總併發量，並將各節點啟動時間錯開 **15 秒**，徹底杜絕同網段併發撞車。
  3. **超時限制拉寬至 40 分鐘**：提供充裕穩健的運行空間，確保 1,002 檔以 100% 成功率完工。

### [2026-08-31] 修訂 10：TPEX 雲端系統性失敗快速中止與單輪驗證
* **問題現象**：
  手動觸發 TPEX-only GitHub Actions 後，TWSE 已正確 skipped，但 TPEX shard 在第 15 檔附近出現連續採集失敗，例如 `3228 (連敗: 15)`，並觸發 WARP 換 IP 與 Chromium 重啟。若繼續等待，會浪費整個 40 分鐘 Runner 時間，且 8 個 shard 會同時消耗 Actions 額度。
* **根因分析**：
  1. 雲端 TPEX 採集一旦進入連續失敗，通常代表 Cloudflare / TPEX Session / Turnstile 門禁已系統性阻擋，繼續跑完整 shard 沒有診斷價值。
  2. 原本雲端 TPEX 仍固定跑 3 輪補抓；當第一輪已出現連敗時，後續補抓只會重複相同失敗模式。
  3. 日誌雖有建立，但 TPEX workflow 在 Python 啟動前有 WARP/Xvfb 安裝與 shard 錯峰 `sleep`，不像 TWSE 一進執行步驟就立刻看到 `[日誌系統]`。
* **修改思維與對策**：
  1. 在 `tpex_crawler_cloud.py` 加入 CI fast-fail 門檻 `TPEX_CI_ABORT_AFTER_CONSECUTIVE_FAILURES`，GitHub Actions 預設 3 檔連續失敗即拋出 `RuntimeError`，讓 shard 明確紅叉，不再白跑。
  2. 將 TPEX 單檔失敗原因寫入 log，例如 `Turnstile Token 逾時`、`API 封包逾時`、`Cloudflare 520 回應`、`非預期回應`，方便後續從 shard log 直接定位阻擋類型。
  3. 修正 coordinator，使 TPEX 也尊重 CLI `--max-rounds`；GitHub Actions TPEX shard 改為 `--max-rounds 1`，把遠端流程改成「單輪驗證、失敗即修」而不是 3 輪等待。
  4. 保留 TWSE / TPEX market input 分流；後續觀察 TPEX 時使用 `market=tpex`，TWSE shard 與 merge-twse 會 skipped。
  5. 在正式 8-shard 前新增 `tpex-probe` 單節點探針，只取 shard 0 前 5 檔驗證 WARP / Turnstile / TPEX Session；probe 成功才展開 8-shard，避免一開始就同時消耗 8 台 Runner。
  6. 新增 `requirements_tpex_cloud.txt` 並將 TPEX probe / shard 改用最小依賴安裝，同時將 TWSE crawler 改為 lazy import，避免 TPEX-only 流程被 TWSE captcha / CNN 重依賴拖慢。

### [2026-08-31] 修訂 11：落實 TPEX Turnstile 全新 Token 門禁與防重用
* **問題現象**：
  TPEX probe log 顯示第一檔即收到 `操作逾時，請重新整理頁面後再試`，隨後被標記為 `Cloudflare 520 回應`，第二檔再度操作逾時後觸發 fast-fail。這表示 probe gate 已能阻止 8-shard 浪費，但雲端單檔查詢仍未完全符合較新文件要求的 Turnstile token 生命週期防護。
* **根因分析**：
  1. 既有雲端 crawler 雖有等待 token，但沒有保存 `last_used_token` 並強制要求新 token 必須與上次送出的 token 不同。
  2. 單檔 token 等待與 API 封包等待仍短於較新根因分析文件建議值，雲端 Turnstile / TPEX API 延遲時容易誤判失敗。
  3. 查詢送出後未主動清空 DOM 中已使用的 `cf-turnstile-response`，下一檔可能讀到殘留舊 token。
* **修改思維與對策**：
  1. `tpex_crawler_cloud.py` 的 `_wait_token()` 改為等待長度大於 50 且 `!= last_used_token` 的全新 token，並在等待期間主動嘗試 `turnstile.execute()`。
  2. 將雲端 token 等待拉長至 30 秒，API 封包等待拉長至 35 秒，符合較新文件的寬裕化配置。
  3. 查詢點擊後立即記錄 `last_used_token`，並清空 DOM 中所有 `input[name="cf-turnstile-response"]` 後呼叫 `turnstile.reset()`，避免下一檔重送舊 token。
  4. 首頁載入後改為實際等待初始 token，並輸出初始 token 長度，讓 GitHub Actions log 能判斷 Turnstile 是否真的就緒。
  5. 若首頁初始 token 長度為 0，不再放行查詢；改為最多 3 次重建 Chromium + WARP reconnect，仍失敗則直接讓 probe 失敗，避免用未建立好的 session 送出查詢。

### [2026-08-31] 修訂 12：TPEX 1000+ 檔分層驗證策略（Probe → Canary → Matrix）
* **問題現象**：
  5 檔 `tpex-probe` 在 fresh-token 修正後可 100% 成功，但正式 8-shard 展開後，各 shard 約在第 12～36 檔陸續出現 3 檔連續 `操作逾時` 並 fast-fail。這證明 5 檔 probe 只能驗證入口可用，不能代表 1000+ 檔長跑穩定。
* **根因分析**：
  全市場 TPEX 約 1000+ 檔，8-shard 後每 shard 約 125 檔；長跑問題通常出現在第 10～40 檔後，必須先用完整單 shard 捕捉長會話、Token 輪替與 TPEX 後端節流問題，再展開其餘 runner。
* **修改思維與對策**：
  1. GitHub Actions 改為三段式 gate：`tpex-probe` 前 5 檔成功後，先跑 `tpex-canary` 完整 shard 0。
  2. `tpex-canary` 成功後才展開正式 matrix；正式 matrix 改跑 shard 1～7，避免 shard 0 重複採集。
  3. `tpex-canary` 產物命名為 `tpex-shard-0`，merge-tpex 仍可用 `tpex-shard-*` 一次聚合完整 0～7 分片。
  4. 若 canary 在第 10～40 檔重現操作逾時，workflow 會停在單 runner 階段，不再同時消耗 8 台 runner。

### [2026-08-31] 修訂 13：TPEX 矩陣併發收斂為序列分片
* **問題現象**：
  套用 fresh-token guard 後，`tpex-probe` 前 5 檔成功，`tpex-canary` shard 0 完整 126 檔成功，但後續 shard 1～7 同時展開後，所有 shard 約在第 22～55 檔間同時出現連續 `操作逾時`，並由 fast-fail 正確中止。
* **根因分析**：
  單一 Runner 長跑 126 檔已被 canary 證實可行；問題出在 canary 後 7 個 Runner 同時查詢 TPEX，總併發仍會觸發 TPEX 後端保護性逾時。這不是單機 Token 流程失敗，而是跨 Runner 併發壓力過高。
* **修改思維與對策**：
  1. 保留 `tpex-probe` 與 `tpex-canary`，先驗證入口與完整單 shard 長跑。
  2. 正式 shard 1～7 matrix 加上 `max-parallel: 1`，改為依序執行，犧牲總耗時換取 TPEX 後端穩定性。
  3. 每個 shard 仍保留獨立 artifact 與 log；merge-tpex 等所有 shard 0～7 產物完成後再彙整。

### [2026-08-31] 修訂 14：操作逾時退避化，禁止單檔重試內反覆重載
* **問題現象**：
  新版 canary-gated workflow 中，部分 probe run 初始 token 已成功取得（長度 752），但第一檔即連續收到 `操作逾時，請重新整理頁面後再試`。log 顯示每次 retry 之間都重新建立首頁 session，形成「逾時 -> reload -> 新 token -> 再逾時」的高頻循環。
* **根因分析**：
  這與較新根因分析文件指出的「失敗一次立刻刷新會引發死循環」一致。操作逾時不是 socket timeout，而是 TPEX / Cloudflare 後端拒絕；在單檔重試內連續 reload 會增加頁面與 Turnstile 負擔，反而更容易被保護機制判定為異常。
* **修改思維與對策**：
  1. 單檔 attempt 收到 `操作逾時` 或其他非預期回應時，不再立即 `_launch_browser_session()` 重建頁面。
  2. 改為清空已用 token、呼叫 `turnstile.reset()`，並做 5～14 秒階梯退避，讓同一 session 有時間背景重簽。
  3. 跨檔連續失敗的重型自癒仍保留在外層門檻處理，避免單檔重試內反覆 reload。

### [2026-08-31] 修訂 15：長會話第 80 檔附近保護性節流的預防性重啟
* **問題現象**：
  操作逾時退避化後，TPEX canary shard 0 從先前中段失敗改善為可連續成功至第 81 檔，但第 82～84 檔連續出現 `操作逾時`，最終 fast-fail。log 顯示第 80 檔後曾觸發既有重啟，但冷卻時間不足，重啟後仍快速進入後端拒絕。
* **根因分析**：
  單一 GitHub Runner 長會話連續查詢 80 檔左右後，TPEX / Cloudflare 對同一出口 IP 或 session 可能累積保護性計數。原本只重啟 Chromium 且等待 1.5 秒，未讓 WARP 出口與 TPEX 後端節流計數充分冷卻。
* **修改思維與對策**：
  1. 將預防性重啟門檻從 80 檔提前到 75 檔。
  2. 重啟時同步執行 WARP disconnect/connect，並加入 5 + 12 秒網路冷卻與 10 秒額外等待。
  3. 重建後仍要求首頁初始 Turnstile token 成功取得才繼續查詢。

### [2026-08-31] 修訂 16：TPEX Probe 自動冷卻重試
* **問題現象**：
  TPEX probe 偶發在初始 token 長度正常（730～752）時，第一、二檔仍連續收到 `操作逾時`，顯示 GitHub Actions / WARP 出口可能正處於 TPEX 保護窗口。若單次 probe 失敗就結束，需要人工重跑，不符合自動化觀察與自癒目標。
* **根因分析**：
  `操作逾時` 有時不是程式流程錯誤，而是短時間內 TPEX / Cloudflare 對當前 runner 出口的保護性拒絕。此狀況應先自動冷卻、重連 WARP、重建 Chromium，再重試 probe，而不是立即要求人工介入。
* **修改思維與對策**：
  1. `tpex-probe` job 內建最多 3 次自動嘗試，環境變數為 `TPEX_PROBE_ATTEMPTS=3`。
  2. 每次 probe 失敗後自動 `pkill` Chrome、WARP disconnect/connect，並冷卻 `TPEX_PROBE_RETRY_COOLDOWN_SECONDS=300` 秒。
  3. probe 任一嘗試成功即放行 canary；三次皆失敗才讓 workflow 紅燈且不展開 canary/matrix。

### [2026-08-31] 修訂 17：正式分片改為同 shard 內多輪補抓，merge 嚴格等待全成功
* **問題現象**：
  使用 canary gate 後，probe 與 shard 0 canary 可成功，但正式 shard 1～7 若在中段遇到數檔 `Cloudflare 520` 或 `操作逾時`，會因 fast-fail 直接結束。這能省時間，但不能自動把失敗標的接到下一批補抓；同時舊的 merge 條件仍可能在 shard failed 時用 partial parquet 產出不完整合併檔。
* **根因分析**：
  1. probe 應該快速判斷入口是否可用，但正式 shard 的 100+ 檔長跑需要容忍少量暫時性 520，交由同 shard 後續輪次補抓。
  2. `merge-tpex` 只檢查 `tpex-shards.result != 'skipped'`，failed matrix 也可能觸發 merge，導致 partial data 被誤當完整資料。
* **修改思維與對策**：
  1. 保留 probe fast-fail；canary 與正式 shard 將 `TPEX_CI_ABORT_AFTER_CONSECUTIVE_FAILURES` 設為 0，避免同 shard 內提前中止。
  2. canary 與正式 shard 改回 `--max-rounds 3`，讓 failed symbols 在同一 runner 內進入下一輪補抓。
  3. canary / shard timeout 拉長至 60 分鐘，提供多輪補抓時間。
  4. `merge-tpex` 改為僅在 canary 與 shard matrix 全部 success 時才執行；`merge-all` 也只接受成功的 merge job，避免 partial parquet 被上傳成完整資料。
